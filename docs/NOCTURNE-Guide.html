NOCTURNE

A Python web console that turns raw monitoring events and ServiceNow history into triaged alerts. Each alert comes with its device and site context, correlated neighbours, ranked past incidents, preliminary checks and a first-response plan. The plan is written by the built-in engine and can be extended by Gemini.

1. Overview

NOCTURNE serves Network Operations Center analysts and the administrators who feed it data. It is a single Python service (FastAPI) that renders its own HTML screens, stores everything in one SQLite file and runs imports in a background worker. Everything is configured in one file, nocturne.toml.

What an analyst gets

  • A live, colour-coded alert console with full-text search, facets and bulk actions.
  • A five-stage triage for any alert: alert analysis, log investigation, ticket history, preliminary checks, recommendation.
  • Device, site and ticket profiles; health scores; outage and flapping analysis.
  • A ready-to-paste ServiceNow work note.

What an administrator gets

  • Data Studio: upload, auto-mapping review, background import, quality reports, event catalogue.
  • Simulator: realistic scenarios, random alerts and custom triggers.
  • User management, role matrix, audit trail and effective settings.
The recommendation engine works without any external service. Gemini is an optional layer on top. Its answers are cached and always labelled, and if it cannot be used the console falls back to the engine and says so.

6. Using each screen

Overview

A navy hero carries six KPIs with change against the previous equal period: open alerts, critical, devices and sites affected, median time to recover, and actionable share. Below it are alerts by hour of day (a "score" of notes by category, coloured by worst severity), the latest unresolved P1/P2 alerts, volume over time stacked by severity, a US state tile map, the noisiest devices, busiest sites, top event types, categories and ticket knowledge. Every bar, note and tile opens the matching filtered list. Windows count back from the newest event, so historical exports read naturally.

Alerts

Colour-coded cards: a severity band (P1 red to P4 teal), a category icon tile, a down/recovered chip, and the IP, site, linked tickets, repeat count and node status. Simulated alerts carry a striped corner and custom alerts a violet one. Search takes words (prefix match), an IP or IP prefix, or a site/FEI code. Facet chips show live counts. The "Show" chip switches between actionable alerts, everything and noise. Cards and compact list views, bulk acknowledge/resolve, CSV export. New alerts slide in live.

Triage

Five stages with a progress rail. Recommended response sits on top with source labels, confidence, evidence, steps you can tick off (remembered per alert), route-to group, typical fix time, the copyable work note and feedback. Alert analysis includes the health ring and the hour-of-day profile. Ticket history shows match % and the reasons for each match. Checks are clearly marked as simulated when they are. Log investigation covers recovery, flapping, site neighbours and the ±24 h timeline.

Devices, sites, tickets

Device profiles show health, activity by day, outages with median recovery, event types, linked tickets, latest events and same-site peers. Site profiles show KPIs, alerts per day, categories, devices with their last node state, latest alerts and tickets. Ticket pages show "what fixed it", the parsed work-note timeline, how each link was made with its confidence, and the extracted facts.

Simulator

Five scenarios run against real devices: random, site outage cascade, flapping interface, power event and WAN failover. You set the count, the pace and an optional site. The custom trigger takes an existing or new device (new ones get their site from the name), a catalogue type or a custom name, a message with {device}, a severity override and a burst count, and previews the classification as you type. A live feed shows everything arriving.

Data Studio and Admin

Data Studio covers knowledge-base totals, drop-zone upload, Mapping Studio review, import history with live progress, quality reports and rejected-row downloads, the event catalogue editor, event and ticket date ranges with an overlap check, Resync with its report, and purges (typed confirmation). Admin covers people (add, role, disable, reset), the role matrix, the audit trail with filters, and effective settings with secrets masked, including AI cache statistics.

Loading feedback

Every wait is visible. A thin progress bar runs under the top bar while any request is in flight. A button that starts work (Resync, Start import, Ask AI, Report, Save) shows a spinner and cannot be pressed twice. Lists and panels show shimmering placeholders until their first data arrives, and dim with a spinner while a filter or time window refreshes them. Live updates and background polling refresh quietly without any of these.

Keyboard: Ctrl/⌘ K or / opens the search palette. g then o, a, d, s or t jumps to a screen, and Esc closes. Day and night themes follow the system and can be switched in the top bar. The layout works down to phone width, where navigation moves to a bottom bar.

7. Import engine (ETL)

7.1 Formats and detection

  • Formats: CSV, TSV, TXT (delimiter sniffed among , ; tab |) and XLSX/XLSM (the sheet with the most rows). Size limit: storage.max_upload_mb.
  • Encoding: UTF-8 (with or without BOM), then Windows-1252, then Latin-1. The ServiceNow export is Windows-1252 and is read correctly.
  • Headers: blank headers become column_N. Rows longer than the header gain extra positional columns. Header matching ignores case, spaces, underscores and punctuation.
  • Dataset detection: each dataset has weighted signature fields, for example events: EventID 2, time 3, type 2, device 2; tickets: number 3, short description 3, created 2, notes 2. The higher score wins, and below 30% the file is "unknown" and the admin chooses.
  • Content sniffing (events): if the column called "Message" holds short, repetitive values while an unnamed column holds long free text, the first becomes the event type name and the long column the message. This is how the SolarWinds export is shaped. A column of 3–5 digit codes becomes a site hint. Time and IP columns are found by pattern when no header matches.
  • Nothing is lost: every unmapped, non-empty value is stored per record in extra (JSON) and shown in triage under "Other columns from the export".

7.4 Timestamps

Every event must carry its own date and time. Nothing is inferred or generated: a row that cannot be dated is rejected with the reason, and the rest of the file imports.

  1. One order per column. Day-first or month-first is decided once for the whole column. A value with a first part above 12 proves day-first (the supplied export: 69,992 such values in "19-05-2026 20:00"); a second part above 12 proves month-first (ServiceNow's "06-24-2026"). With no proof either way, the reading that gives the tighter date span wins (1–3 May rather than 5 Jan – 5 Mar); a tie uses etl.dates.ambiguous_order (events day-first, tickets month-first). If a column mixes both shapes, rows that prove their own order are read that way and ambiguous ones are rejected.
  2. Every row is checked, and failures land in the rejects file: Missing timestamp, Time without a date, Date without a time, Invalid date (31-02-2026), Date before 2000 (earliest_year), Date in the future (beyond future_tolerance_hours, 48).
  3. Time-only files are refused as a whole with a clear message when most values are bare clock times, so a wrong mapping cannot quietly reject a whole export. Mapping Studio warns about this before the import starts and shows the detected order with its evidence.
  4. Precision. The supplied export has minute precision, so several events can share a minute. Everything that orders events (alert lists, outage pairing, timelines, latest node state) breaks ties by EventID. Against the earlier export that carried seconds, EventID order matches the true order for 99.99% of same-minute neighbours (105,888 of 105,898).

7.6 Sites, devices and roles

  • Site code from device name (etl.extract.site_from_device): 0412-Dallas-TX-… → 0412, feisw030.ustxhouston1502.int… → 1502, 1440A-Apex-NC → 1440. Codes are canonical and zero-padded, so "412" and "0412" are the same site.
  • Site column trust rule: the unnamed site column in the supplied export matches device names for only 55.7% of devices, so it is ignored there. In the test export it matches 100% and is used as a fallback.
  • Site label: from device names (Santa-Clara-CA → "Santa Clara, CA") or from location text ("Dallas TX 75201").
  • Device role: regex rules over name, model and vendor, giving switch, access point, router, firewall, UPS, controller, printer or device. Roles drive icons, playbook wording and simulator choices.

7.7 Quality report and rejects

Each finished import stores a report (Data Studio → Report):

  • rows read, new, updated, unchanged, skipped as older, rejected and duplicated within the file, plus repaired multi-line fields
  • new and updated devices, sites seen
  • timestamps: detected order with its evidence, precision, first and last event, days covered; for tickets also stated start times used and ignored, and status changes

8. Classification

All rules live in [classification]. They are case-insensitive regular expressions, and the first match wins.

  • Category (tried on the event name first, then the message): monitoring, inventory, power, wireless, routing, hardware, performance, interface, connectivity, other. Name-first matters: "Interface Down … Smart APC UPS Management" is an interface event, not a power event.
  • Actionable = severity in actionable_severities and category not in noise_categories (monitoring, inventory). 45% of the supplied events are actionable.
  • Transition: the last state word wins ("…changed to DOWN" → down, "…restored to UP" → up). "Uplink" and "UPS" do not count as "up".
  • Pair key: device plus interface (Gi1/0/46, TenGigabitEthernet1/0/1, Port 24, vni-0/1 …), or device plus "node". This pairs each down with the up that clears it.
  • Event catalogue: 56 type names were derived from the message patterns in the export (e.g. 5000 Alert Triggered, 604 Thin AP Disappeared, 6808 UPS On Line). Admins can rename types and pin severity or category, and saving re-classifies that type's existing alerts.

With the supplied 30-day exports, 316 of 442 tickets are linked (71%): 48 device links, 37 IP links and 370 site links.

9.1 Time evidence

Alert timing is used to confirm or question a link only where it is real evidence:

  • Incident anchor. Many tickets state when the incident began ("Start time: 07/08/26 1:19 AM"). In the supplied tickets 72 do; their gap to the ticket opening is 0.1–11.4 h for nearly all (median about 2.5 h), which shows both use the same clock. A stated start is trusted only between stated_start_max_hours_before (24 h) before and stated_start_max_minutes_after (15 min) after the opening; 66 qualify, and 6 are ignored (start 3–8 h after opening, 43 h or a month earlier, one dated December). Without a usable start, the opening time is the anchor.
  • Confirmation. A P1–P3 alert on the linked device (or, for site links, at the site) within ±start_window_minutes (60) of a stated start, or from confirm_hours_before (24 h) before to confirm_hours_after (2 h) after the opening, confirms the link: +confirmed_bonus (0.15, capped at 0.99) and the alert is shown on the ticket.
  • Silence. When imported events cover the whole window and show nothing, a site-only link drops to site_without_alerts (0.45). Device links keep their confidence, since a device named in the text is strong evidence on its own.
  • No coverage. Days without imported events say nothing, so links there keep their text-based confidence. Recommendations do the same: when an alert falls outside the period the tickets cover, ticket timing is left out and the link and wording weights are rescaled (0.5 and 0.3 become 0.625 and 0.375), instead of every ticket losing 20 points for being "far away".

On the supplied exports the tickets (12 Jun – 13 Jul) and events (26 Apr – 19 May) do not overlap, so all 455 links are "outside event data". A constant shift between the two exports was ruled out before deciding this: for device-linked tickets, the day gaps to their devices' critical alerts spread evenly from 40 to 68 days, with the most common gap holding only 14% of tickets, and the ticket work notes cite June and July dates more than 1,500 times. Aligning one export to the other would therefore invent dates, so it is not done. Data Studio shows both ranges and flags when they do not overlap.

9.2 Resync

Data Studio → Resync (and the end of every import and purge) rebuilds everything derived from the stored data: device counters, latest status and IP from each device's newest event, the site registry, all ticket links with their time evidence, and the search indexes. Events alone, tickets alone, both in either order, re-uploads and purges all end in the same state. Tickets uploaded before any events have nothing to link to yet; the resync report counts those that name sites with no events (59 for the supplied tickets once events are in, 367 when tickets are loaded alone) and they link as soon as those events arrive. A resync of the supplied data takes under a second.

10. Correlation and health

  • Outages: the first "down" of a streak opens an outage and the next "up" with the same pair key closes it. Duration feeds the median time to recover (MTTR) and P90. A down with no matching up counts as "still down".
  • Flapping: at least flap_threshold (3) closed outages of ≤ flap_window_minutes (60) on one device.
  • Blast radius: other devices at the same site with a "down" within ±blast_radius_minutes (15). This drives the "site-level disruption" hypothesis and the single parent ticket advice.
  • Recurrence: the same event type on this device and at this site over the last 7 days, plus the device's hour-of-day profile.
  • Health score (0–100) over health_window_days up to the device's latest activity: 100 × e^(−penalty/60), where penalty = 8·P1 + 4·P2 + 1·P3 + 6·flap cycles + 5·open tickets. Grades: Healthy ≥ 80, Watch ≥ 55, Degraded ≥ 30, otherwise Critical.

11. Recommendations (built-in engine)

Ticket candidates come from three places: links to the device, links to its site (including tickets about other devices at the same site), and an FTS5 query built from specific words in the alert, with generic words such as "lost", "node" and "status" removed. Each candidate is scored (diagram 4.2) and shown with readable reasons: "names this device", "mentions site 0412", "shares dallas, switch, uplink", "opened 0 min after this alert", "marked helpful by analysts 2×".

The plan combines several parts:

  • A hypothesis chosen by evidence priority.
  • An avoid duplicate step when an open INC is tied to the device, or to the site at the same time.
  • Correlation steps for site-wide drops and flapping.
  • The category playbook from [playbooks], with device, IP, site and interface filled in.
  • "Worked in INC…" steps from strong matches (score ≥ min_fix_score).

Each step shows its source. Analyst feedback ("this ticket helped") boosts that ticket for the same device or event type in later triage.

13. Preliminary checks

[diagnostics] mode:

  • simulated (default): deterministic results that follow the device's last known node state. A device whose last node event is "down" fails ping, its traceroute stops at the site gateway and its ports are closed. Results carry a striped "Simulated results" badge and say so in the work note.
  • live: runs ping and traceroute (or tracert on Windows) as subprocesses without a shell, does DNS in Python, and checks TCP ports (tcp_ports) with socket connects. Hosts are validated against a strict IPv4/hostname pattern before anything runs, and every check has a hard timeout.

Results are cached per host and state for cache_seconds. In live mode, ad-hoc checks (POST /api/diagnostics) only target device IPs and names in the inventory while adhoc_known_hosts_only is true (the default), so the console cannot be used to probe arbitrary hosts.

Indexes cover the console's access paths: time, device and time, site and time, severity and time, type, state, IP, actionable and time, and pair key. Most are covering (they hold every column the query reads), so dashboard aggregates, alert facet counts, outage pairing and site roll-ups read an index instead of visiting each row. The dashboard is built from two scans of the window (an hourly roll-up and a device × site roll-up) rather than one scan per chart. Planner statistics are refreshed (PRAGMA optimize) at the end of every resync.

Query cache (app/cache.py): derived results are cached under the current data version, which every write that changes what screens show increments (imports, resync, purges, catalogue edits, alert state changes, feedback, simulated and custom alerts). A cached value is therefore never stale, and because the version lives in the database this holds across several app processes. Cached: the dashboard, alert-console totals and facet counts (reused across pages and sorts of the same filter), triage stages 2, 3 and 5 per alert, device counts, the sites list, site profiles, Data Studio summary and catalogue figures, simulator options and ticket date ranges. Concurrent requests for the same missing value share one computation; the cache holds at most 512 entries, and Admin → Settings shows its entries, hits, misses and hit rate.

19. Security

  • Passwords: scrypt (N=2¹⁴), at least 10 characters mixing three character classes, forced change for new and reset accounts. Repeated failures lock the username from that client address (so nobody can lock a colleague out from elsewhere) and cap guessing across usernames from one address; unknown usernames take as long to refuse as wrong passwords.
  • Sessions: recorded server-side; the signed, HTTP-only, SameSite=Lax cookie carries only the session id and expires after 12 hours. Signing out ends the session at once; changing a password ends every other session; an administrator's reset or disable ends all of that user's sessions. The user is re-checked as active on every request. Set cookie_secure = true behind HTTPS.
  • CSRF: a per-session token is required in the header on every write.
  • Authorisation: capability checks on every API endpoint and page. At least one active administrator is always kept.
  • Input safety: parameterised SQL throughout, sanitised upload names, strict host validation before diagnostics, no shell execution, HTML-escaped rendering, malformed filter values refused with 400. CSV exports prefix cells that start with = + - @ so spreadsheets show them instead of running them.
  • Headers: Content-Security-Policy (same-origin resources only, no framing), nosniff, frame denial, same-origin referrer, no-store on the API. The client address in the audit trail is the connecting address; X-Forwarded-For is applied only for proxies trusted by uvicorn's --forwarded-allow-ips.
  • Audit: sign-ins (including failures and throttled attempts), imports, cancelled imports, purges, catalogue edits, state changes, exports, diagnostics, simulations, AI refreshes and user changes.
  • AI: only alert evidence and ticket summaries are sent; credentials, users and audit data never are. The key is read from the environment.
For shared deployments, put NOCTURNE behind HTTPS (reverse proxy) and set NOCTURNE_SECRET_KEY and NOCTURNE_ADMIN_PASSWORD.

20. Operations and scaling

  • Performance, measured on a synthetic export the size of the supplied one (134,000 events, 5,918 devices, 442 tickets, 28 MB): import about 8 s, resync about 0.3 s. Dashboard "All" 0.33 s cold (was 1.1 s) and about 3 ms cached; alert list with facets 37 ms on the first view of a filter and about 3 ms when paging (was 190 ms); devices list about 4 ms (was 1.2 s); sites list 76 ms cold, 2 ms cached (was 140 ms); triage recommendation about 3 ms (was 0.64 s, which included a 0.6 s display pause now applied only to the visible checks stage). JSON responses are gzip-compressed (the live stream never is); fonts and images are cached by browsers and CSS/JS revalidate with ETags.
  • Backups: copy data/nocturne.db (WAL mode is safe to copy with SQLite's backup API or while the service is stopped) and data/uploads.
  • Restarts: queued imports resume. Running ones are marked "interrupted" and re-run with one click, and upserts make re-runs safe.
  • Scaling path: the services are stateless apart from bus.py (in-process pub/sub) and runner.py (one worker thread). For several app instances, swap the bus for Redis pub/sub and the runner for a queue worker, and move SQL to PostgreSQL (replacing FTS5 with tsvector). Routers and services stay the same.
  • Troubleshooting:
    • A wrong mapping can be fixed in Mapping Studio, then use "Run again".
    • If dates look wrong, choose "Newest day is the date on the right" with the correct date.
    • For few ticket links, check the quality report's "mentions_*" coverage and add site patterns in [etl.extract].
    • If AI shows Fallback, read the reason shown above the plan.
